# AGENTS.md

Guidance for any AI agent (Claude, other assistants, etc.) working in this repository.

## Project purpose

This is a Unity project whose goal is to build a **simulation environment connected to ROS 2**,
in order to simulate an autonomous robot. The specific robot (its form factor, sensors,
actuators, and task) has **not been decided yet** — treat the project as a generic
"Unity ↔ ROS 2 sim" scaffold until the user picks a concrete robot. Don't assume a wheeled
robot, arm, drone, etc. unless the user has stated one; ask if it's unclear and it matters
for the task at hand.

The eventual shape of the work is roughly:
1. A Unity scene acting as the simulated world (environment, physics, robot model).
2. A bridge between Unity and ROS 2 so ROS 2 nodes can send commands / receive sensor data
   to and from the simulated robot.
3. A robot description (URDF or hand-built rig) driven by Unity physics (`ArticulationBody`).
4. Eventually, autonomy logic living on the ROS 2 side (or partly in Unity) that consumes
   simulated sensors and issues commands.

## How to work with the user on this project — read this first

**This project exists for the user to learn**, not just to get a working robot sim as fast
as possible. This changes how you should operate compared to a typical "get it done" task:

- **Teach, don't just deliver.** Before wiring something up, explain what you're about to do
  and why — what the piece is for, how it fits into the Unity↔ROS2 architecture, and what the
  alternatives were. Prefer walking the user through a step (with them making edits or running
  commands themselves) over silently doing everything and presenting a finished result.
- **Default to smaller, understandable steps** over big one-shot scaffolds. If a task could be
  done as one large autogenerated dump of files vs. an incremental build-up, prefer the latter.
- **Check understanding, don't assume it.** The user may be new to Unity, to ROS 2, or to both.
  Don't assume familiarity with terms like `ArticulationBody`, DDS, nodes/topics/services, URDF,
  coordinate frame conventions (Unity is left-handed Y-up; ROS is right-handed Z-up — this trips
  everyone up eventually), etc. Briefly explain a concept the first time it becomes relevant.
- **It's fine to just do routine, non-educational work** (formatting, fixing a typo, a trivial
  config tweak) without turning it into a lesson — use judgment about what's actually worth
  explaining.
- **When there's a decision with real tradeoffs** (which ROS 2 distro, which bridge package,
  URDF vs. hand-built rig, WSL2 vs. dual-boot vs. Docker), lay out the tradeoffs and let the user
  decide rather than silently picking one, unless they've asked you to just pick.

## Phase 1–5: Unity-only robot prototype (done)

Before touching ROS 2, we built and tuned a self-contained Unity prototype: a room, a wheeled
robot, a simulated lidar, and reactive obstacle avoidance — all pure Unity/C#, no networking. The
goal was to learn the sim-building mechanics and the classic pitfalls of reactive robot navigation
before adding ROS 2's complexity on top.

- **Environment**: `Assets/Scenes/RobotRoom.unity` — a large room (floor + walls) with scattered
  obstacle primitives, an empty `StartCorner` marker in one corner, and an empty `Exit` marker at a
  gap in one wall.
- **Robot**: a `Robot` GameObject (root has the `Rigidbody`, X/Z rotation frozen so it can't tip
  over) with child meshes for the chassis and wheels (visual only — no `WheelCollider`s, movement
  is a simple kinematic-style drive, not full wheel physics). Driven by three scripts in
  `Assets/Scripts/`:
  - `RobotDrive.cs` — exposes `SetVelocity(forwardSpeed, turnSpeed)`, normalized -1..1 inputs
    applied to the `Rigidbody` in `FixedUpdate`. Deliberately mirrors ROS's `cmd_vel`
    (linear.x / angular.z) convention so a future ROS 2 bridge just has to translate an incoming
    message into this same call.
  - `LidarSensor.cs` — casts a configurable fan of raycasts each frame and exposes a `Ranges[]`
    array (distance per ray, `maxRange` if no hit) plus `GetRayDirection(i)`. This is a stand-in
    for a real lidar's `/scan` (`sensor_msgs/LaserScan`) data.
  - `NavigationController.cs` — reactive "potential field" style steering: blends a goal-seeking
    vector (toward the `Exit` marker) with an obstacle-repulsion vector built from any lidar ray
    under `avoidanceRadius`. Required several rounds of tuning to fix real failure modes we hit
    live (see below) — the current version has a symmetry-breaking bias, turn-rate limiting, a
    minimum forward speed while turning, and squared distance falloff so the nearest obstacle
    dominates.

### Known limitation, deliberately not fixed further
In narrow gaps between multiple close obstacles, the robot still swerves more than necessary
("drunk walking") — reacting to every nearby ray omnidirectionally rather than reasoning about
whether an obstacle actually blocks its path. We discussed this with the user and decided **not**
to keep hand-tuning it: that's precisely the job of a real local planner (ROS 2 Nav2's DWA/TEB,
which reason about the robot's actual footprint against a costmap), and hand-rolling that logic
here would mean re-implementing Nav2 piecemeal only to throw it away once ROS 2 is wired in. Revisit
proper path planning in the ROS 2 phase (or a later VLA-based navigation phase) rather than
continuing to patch the reactive script.

### Debugging note for future agents
Unity's Inspector **Transform "Position" field shows local position (relative to the parent), not
world position** — this bit us once when trying to move a parent to line up with its children
without disturbing their visual placement. The reliable fix, if this comes up again: unparent the
children (drag to top-level in the Hierarchy — this preserves world position), read their now-
accurate Position values, move/set the parent's transform, then re-parent (again preserves world
position, so Unity recalculates each child's local transform for you).

## What's needed for the Unity ↔ ROS 2 goal (not installed yet)

These are things the project will need as it grows. None of this is installed — treat this as a
map for planning, and add things incrementally as the user actually gets to that stage, explaining
each as it's introduced.

### 1. A running ROS 2 install
Unity itself doesn't run ROS 2 — ROS 2 needs to run somewhere Unity can reach over the network
(usually `localhost`). On Windows, the common options are:
- **WSL2 + Ubuntu**, running ROS 2 natively inside — most common for Windows + ROS 2 learning setups.
- **Docker** (e.g. `osrf/ros:jazzy-desktop`) — reproducible, avoids polluting the machine.
- Native Windows ROS 2 builds exist but are less common/well-trodden than Linux.

Distro choice: **ROS 2 Jazzy** (current LTS, supported into 2029) or **ROS 2 Humble** (older LTS,
huge amount of existing tutorials/packages still assume it). Worth discussing with the user rather
than assuming.

### 2. A Unity ↔ ROS 2 bridge (pick one)
- **`ROS-TCP-Connector`** (Unity package) + **`ROS-TCP-Endpoint`** (ROS-side package) — from
  Unity's "Unity Robotics Hub". Simplest to learn, most tutorials, JSON/TCP-based bridge. Installed
  via Package Manager → "Add package from git URL":
  `https://github.com/Unity-Technologies/ROS-TCP-Connector.git?path=/com.unity.robotics.ros-tcp-connector`
- **`ros2-for-unity`** (RobotecAI) — a native rclcpp/DDS bridge (not just a TCP/JSON relay),
  more actively maintained, supports recent ROS 2 distros, more setup work (needs ROS 2 libraries
  built for Unity to link against). Better long-term fit, steeper initial setup.

This is a real tradeoff worth walking the user through rather than picking silently.

### 3. Robot description / model
- **`com.unity.robotics.urdf-importer`** (Unity Robotics Hub) — imports a ROS-style URDF robot
  description into Unity as a rig of `ArticulationBody` joints. Useful once the user has picked
  a robot with an existing URDF (e.g. TurtleBot, a robot arm).
- `ArticulationBody` itself is **built into Unity's physics engine already** (no package needed)
  — it's the right tool for robot joints/links (vs. plain `Rigidbody` + `Joint` components), since
  it's designed for articulated, physically accurate robot chains.

### 4. Optional, depending on what the robot needs
- **`com.unity.perception`** — synthetic data / camera-sensor tooling, useful if the robot needs
  simulated cameras for a perception task.
- **`com.unity.cinemachine`** — camera rigs, mainly a convenience for observing the sim, not
  required for the robot itself.
- Custom sensor simulation (LIDAR, depth, etc.) generally means hand-rolled raycasting/rendering
  code — Unity doesn't ship an official LIDAR package.

### Not yet needed
Don't add any of the above until it's actually relevant to the step the user is working on —
listing them here is for planning, not a to-do list to execute immediately.
